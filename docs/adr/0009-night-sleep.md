# ADR 0009 — 夜间息屏：面板靠写黑，不确定一律亮着

- 状态：已采纳
- 日期：2026-08-13
- 相关：[ADR 0006](0006-no-flythings-network-managers.md)（不链接 FlyThings 网络管理器）、
  `device/tc002-os/app/src/ui/SleepPolicy.h`

## 背景

用户要的是「手机式息屏」：设一个夜间时段，时段内长时间无人操作就息屏，在 GUI 或实体机上
操作一下就重新计时。

**用户看到的字一律是「息屏」，不是「休眠」。**中文语境里 休眠 是 hibernate——机器断电——
在一台唯一恢复手段就是断电的设备上，这正是会劝退用户的那个联想；手机说的是 息屏 / 自动锁屏。
prefs 键和线协议键仍然是 `sleep.*`：那是给机器读的，改名只会换来一次迁移。

这个功能的失败方向只有一个，而且极其昂贵：**一块黑着、回不来的面板**。用户唯一的自救手段
是断电重启，而一段错误的时间窗会在重启后**原样复现**。所以下面两条不是实现细节，是这个
功能能不能上机的前提。

## 决策一：面板靠**主动写黑帧**变暗，而不是停止渲染、不是调亮度、不是关 MCU

四个候选，三个必须排除：

- **停止渲染 —— 会冻结画面，正好是功能的反面。** `Presenter::present` 把整帧时钟进 MCU，
  面板由 MCU 自己驱动，**它会保持最后一帧**。README 里那条自己的教训就是证据：少了
  `queryMcuVersion()` 的握手，「面板停在 MCU 自己的开机画面」而渲染循环照跑。所以「不写」
  等于「画面定格」。
- **`McuManager::powerOff()` —— 没有唤醒路径。** 这台机器唯一的恢复手段是物理按键，一个
  能把设备关掉却唤不醒的分支不该存在于自动逻辑里。
- **亮度调到 0 —— 既到不了黑，又会留下后遗症。** `DeviceControls::kBrightnessSteps` 里
  没有 0，`scaleByte` 还有一个 floor(1)（存在的理由是「变暗不能删掉内容」），而且亮度是
  **持久化**的——一次断电就可能把用户的时钟带回一块很暗的面板。
- **写黑帧（采纳）。** 息屏时清空画布并 `present(canvas, 0)`；淡出是 `Presenter` 每帧路径里
  的一个整数百分比，**不存任何状态**，所以断电不可能带回一块变暗的面板。

黑帧的重绘频率是 **1 Hz，不是 0 也不是 50 Hz**。不是 0：`spi.write()` 会失败（Presenter 自己
就在记这条日志），一帧丢掉的黑帧会让面板亮一整夜而没有任何东西来纠正它——1 Hz 是自愈的。
不是 50 Hz：那是每秒 ~156 KB SPI 加 750 ms 的 `usleep`，而省下来的就是这些。**真正耗电的是
832 颗 LED**，发零字节就已经拿到了；SoC 那 4% 是毫瓦级，为它去碰一个唯一恢复手段是断电的
部件，即使有对应的 opcode 也是坏交易。

**20 ms 的 tick 不降频。** 它是唯一在排空按键队列、轮询链路、提交 prefs 和决定唤醒的东西；
降到 200 ms 就是在旋钮转动和面板亮起之间插进最多 200 ms——而那恰好是用户在评判这个功能的
那一刻。省下的是 render + present 这对昂贵的操作，50 次里跳过 49 次。

## 决策二：**每一种时间上的不确定，都解析为一块亮着的面板**

这台设备在 TimeSync 出现之前实测停在 1970-01-01 00:00，而 1970-01-01 00:00 **就在
23:00→07:00 这个窗口里面**。一个天真的实现会在每次开机后的 `idle` 内把面板抹黑，用户看到
一台永远不亮的时钟，而最显然的自救动作——断电重启——会精确地复现它。这在用户眼里就是砖。

所以 `decideSleep()` 的每一条 guard 都朝同一个方向倒：

| 条件 | 结果 |
|---|---|
| 从未同步 (`clockSynced == false`) | 永不息屏 |
| 同步过但没有单调时间戳 (`clockAgeMs < 0`) | 永不息屏 |
| 上次同步早于 **26 小时** | 永不息屏 |
| `idleMs <= 0`（prefs 损坏） | 永不息屏 |
| 负的 idle（单调时钟 24.8 天回绕） | 永不息屏 |
| 电量低导致的关机倒计时挂起 | 永不息屏 |

**26 小时**是一个有理由的数：它超过一整天，所以一个下午的 DNS 故障不会让设备当晚失去息屏
能力（漂移只有几秒）；它又是有界的，所以一台离网一周的设备不会依据一个没人核对过的时钟把
自己抹黑。走到 26 小时意味着四台 NTP 服务器一天多都联系不上——那时控制台也早就看不到这台
设备，用户已经知道了。**在第一次同步失败就禁用息屏是错的**：23:05 的一次路由器重启会让卧室
亮一整夜。

墙上时间和单调时间**从不混用**：窗口比对墙上时间（`time(NULL)` 加固定的 +8，这个 rootfs 没有
tzdata，`localtime()` 会静默返回 UTC），倒计时只用 `CLOCK_MONOTONIC`。这就是第一次校时那
56 年的跳变不可能污染倒计时的原因；它可以瞬间翻转窗口判定，而那正是正确行为。

## 由此得到的安全网

没有任何一条失败路径能把面板永久留在黑屏：

1. 任意按键唤醒——判定在输入排空处、任何路由之前，所以在任何页面任何状态都成立。
2. **窗口关闭自动唤醒**，无需任何操作。这是最重要的那条安全性质：存在一个**确定的墙上时刻**，
   面板会自己回来。
3. 上表六条不确定全部解析为亮着。
4. `sleep.enabled` 默认 0，刚刷的固件在被要求之前不会自己息屏。
5. 息屏**从不触碰 `DeviceControls`**，断电回来不可能变暗。
6. **没有可以卡住的「已息屏」状态位**——每 20 ms 从
   `(now, config, lastActivity, clock)` 重算一遍。
7. 控制台 `PUT /api/os/sleep {enabled:false}` 在 8 秒轮询内到达，并且**当场**点亮面板：
   上升的序列本身就算一次用户操作。第 7 条能不能兑现取决于**序列**：hub 的计数器是 Bun 进程
   里的普通实例状态，服务一重启就回到 1，而设备还记着上次采纳的号。所以设备把**变小的序列**
   当成「服务重启了」而不是「重放」（`applySleepRequest`），否则这条逃生口在最常见的部署状态
   下是死的——路由照回 200，什么都不会发生。

**旋钮上到不了 `全天`。**第 2 条那个「确定的墙上时刻」是全部安全论证的支点，而 `全天`
（`start == end`）恰好没有它。它曾经就排在 `00-08` 后面一档：一个只是想看看这一行是什么的
用户，两下就能把夜间息屏变成全天屏保，而且下一档 `关闭` 记住的窗口也成了全天。现在它只在
线协议上存在——控制台的表单可以给它加标题和说明，一块 52 px 的行不能。固件仍然照常执行它，
自检里有一条断言：从任何起点（包括控制台设的 `全天`）连按 24 次旋钮，都到不了一个
`start == end` 的窗口。

## 代价

- 息屏期间每秒一次 SPI 写和一次 15 ms `usleep`，换来对单次 SPI 失败的自愈。
- **音乐照放，游戏引擎不走。**`base::AudioPlayer` 不在渲染路径上，所以播放完全不受影响；而
  `GameScreen::render` 才是调 `mEngine->tick(dt)` 的地方，息屏时那一支换成了
  `canvas().clear()`，所以引擎整夜不动。这是安全的：醒来那一帧 `dt` 被夹在 250 ms，八小时的
  空档不会把球瞬移穿墙。**别去「修」它**——把 `shell().render()` 提到 `repaintDue` 之外会让
  render+present 回到每秒 50 次，还会以 1 Hz 的粒度去戳引擎。写在这里是因为这条 ADR 原先声称
  「游戏继续跑」，而代码从来不是这样。
- 窗口结束时面板会**无人值守地醒来**，回到当时压在最上面的那个页面——包括一个恢复运行的游戏，
  它可能会出声。这是第 2 条安全性质的代价，接受：一个到点自己回来的面板，比一个需要人来救的
  黑面板便宜得多。
- 没有基于内容的豁免（「放音乐时不息屏」）。用户选窗口和超时的时候已经说明了他夜里要什么；
  一条「音乐豁免」意味着另一台设备上忘关的 Spotify 会照亮卧室一整夜——那正是这个功能要解决
  的抱怨；而一条让面板有时息屏有时不息屏的隐形规则是无法调试的。真要的话它应该是一行显式的
  「播放时不息屏」设置，而不是藏起来的行为。
